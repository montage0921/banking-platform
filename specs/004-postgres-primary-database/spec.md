# Feature Specification: Postgres as the Primary Application Database (H2 Removal)

**Feature Branch**: `[to-be-set-by-git-hook]`

**Created**: September 3, 2026

**Status**: Draft

**Input**: User description: "The application currently uses an H2 in-memory database, which is not suitable for multi-environment testing or consistent data across features. This ticket introduces Postgres as the shared database for development, QA, and demo environments. Ensure the entire Voltio application runs on Postgres instead of H2, with stable data that persists across runs and supports all features. Set up a Postgres database for dev, QA, and demo environments; move the existing schema and seed data into Postgres; update the application so it connects to Postgres instead of H2; remove H2 from the project; confirm all features work normally using Postgres. This is a technical infrastructure ticket, not a user story. No customer-facing behavior changes. No feature logic changes."

## User Scenarios & Testing _(mandatory)_

### User Story 1 - The application runs on Postgres and data survives a restart (Priority: P1)

A developer starts the backend, creates an account and posts a transaction, stops the backend, and starts it again. The account and transaction are still there, in a Postgres database, with no H2 file involved anywhere.

**Why this priority**: This is the ticket's core objective. Every other story is either a precondition for this one or a verification of it.

**Independent Test**: Start the backend against a running Postgres, exercise one write endpoint, restart the backend, and read the same record back through its API.

**Acceptance Scenarios**:

1. **Given** a running Postgres instance and no H2 file on disk, **When** the backend starts, **Then** it starts successfully and every JPA repository resolves against Postgres.
2. **Given** the backend has written records through its normal endpoints, **When** the backend is stopped and started again, **Then** those records are still readable through the same endpoints with identical values.
3. **Given** the backend is running, **When** the effective datasource configuration is inspected (startup log, actuator, or connection metadata), **Then** the primary datasource reports a PostgreSQL product and driver, not H2.
4. **Given** the chatbot's separate pgvector datasource, **When** the primary datasource moves to Postgres, **Then** the chatbot's knowledge base and `chat_interaction_log` continue to resolve through their own `chatbotVectorJdbcTemplate` as they do today, unchanged.

---

### User Story 2 - Schema is versioned and applied identically on every environment (Priority: P1)

Schema today is produced by `spring.jpa.hibernate.ddl-auto=update` plus a single H2-dialect script run through `spring.sql.init`. That combination is what allowed a developer's `audit_log` table to silently lack `actor_type`, then `event_type`, and fail at runtime rather than at startup. On Postgres, schema comes from ordered, versioned migrations instead.

**Why this priority**: The Definition of Done requires that running the same scenario twice produces the same result. That cannot hold while schema is derived from whatever state a given machine's database happens to be in.

**Independent Test**: Point the application at an empty Postgres database, start it, and verify the full schema is created by migrations; then start it again and verify no schema changes are attempted on the second boot.

**Acceptance Scenarios**:

1. **Given** an empty Postgres database, **When** the application starts, **Then** all migrations apply in order and the resulting schema supports every entity in the application without further modification.
2. **Given** a database already at the current migration version, **When** the application starts again, **Then** no migration is re-applied and startup succeeds.
3. **Given** an entity whose mapping does not match the migrated schema, **When** the application starts, **Then** startup fails with a clear validation error naming the mismatch, rather than starting successfully and failing later at query time.
4. **Given** a developer adds a new column to an entity without a corresponding migration, **When** they start the application, **Then** the mismatch is caught at startup (per Scenario 3), making the missing migration obvious before any runtime error can occur.

---

### User Story 3 - Seed personas load into Postgres and are reproducible (Priority: P1)

`backend/scripts/seed_demo_data.sql` (generated by `generate_seed.py` with a fixed RNG seed) provides 100 customers, 235 accounts, 26,170 transactions and 89 savings goals, deliberately spread across risk personas (45 healthy, 32 comfortable, 14 stretched, 9 strained) so Risk, Insights and the chatbot all have data in every band. That seed must load into Postgres and produce the same state every time.

**Why this priority**: "Seed personas load properly" is an explicit Definition of Done item, and the persona spread is what makes the other feature areas demonstrable at all.

**Independent Test**: Load the seed into a freshly migrated Postgres database, query the persona customer IDs, and confirm the documented counts per risk band; then unseed, re-seed, and confirm the same counts and balances.

**Acceptance Scenarios**:

1. **Given** a freshly migrated, empty Postgres database, **When** the demo seed is applied, **Then** it completes without error and produces the documented row counts (100 customers, 235 accounts, 26,170 transactions, 89 savings goals).
2. **Given** the seed has been applied, **When** the application subsequently creates a new customer, account, transaction or savings goal through its normal endpoints, **Then** the insert succeeds without a primary-key collision against the explicitly-numbered seed rows (see Edge Cases: identity sequence desync).
3. **Given** a seeded database, **When** `unseed_demo_data.sql` is run and the seed is applied again, **Then** the resulting data is equivalent to the first seeding, with no duplicate or orphaned rows.
4. **Given** a seeded database, **When** a QA scenario is executed twice from the same starting state, **Then** both runs observe the same data and produce the same result.

### User Story 4 - Every feature area behaves normally on Postgres (Priority: P2)

Chatbot, Agent (confirmation gate), Tools, RAG, Insights, OPS (account freeze/unfreeze and its control history) and Risk all read and write through the primary datasource. Each must be exercised against Postgres before this ticket is done.

**Why this priority**: The ticket's Definition of Done names these areas explicitly. It is verification of Story 1 rather than new capability, so it sits below the stories that make it possible.

**Independent Test**: With a migrated and seeded Postgres, run one representative read and one representative write per feature area and confirm behavior matches the pre-migration baseline.

**Acceptance Scenarios**:

1. **Given** a seeded Postgres database, **When** a chat turn is sent to `/api/chat/savings-insights`, **Then** it returns a response, writes its `chat_interaction_log` row on the chatbot datasource, and writes its shared `audit_log` row on the primary Postgres datasource.
2. **Given** an agent transfer proposal, **When** the customer confirms it through `/api/chat/confirmations/{token}`, **Then** the pending action row, the resulting transfer and both audit rows persist correctly on Postgres.
3. **Given** an admin freezes and then unfreezes an account, **When** the control history endpoint is called, **Then** it returns both events from `account_control_audit`, and the corresponding `ACCOUNT_FROZEN`/`ACCOUNT_UNFROZEN` rows are present in the shared `audit_log`.
4. **Given** seeded transaction history, **When** Insights and Risk are requested for customers in each persona band, **Then** each returns a result consistent with the pre-migration baseline for the same customer.
5. **Given** any feature area writes an audit row, **When** the write occurs, **Then** it succeeds against the Postgres `audit_log` table with no missing-column error.

---

### User Story 5 - Repository and integration tests run against real Postgres (Priority: P2)

Thirteen repository test classes and `AuthCustomerIntegrationTest` currently use `@DataJpaTest` against an embedded H2 database. Removing H2 from the project requires giving those tests a real database, and doing so removes the dialect gap between what tests validate and what production runs.

**Why this priority**: Required by "H2 is fully removed from configuration and dependencies", and it is the only way the test suite can catch Postgres-specific defects. Below P1 because the application shipping on Postgres does not depend on it.

**Independent Test**: Run the backend test suite with no H2 artifact on the classpath and confirm the repository and integration tests pass against a Postgres container.

**Acceptance Scenarios**:

1. **Given** H2 is absent from the build entirely, **When** the test suite runs, **Then** every repository and integration test executes against a Postgres instance and passes.
2. **Given** the test suite runs twice in a row, **When** the second run starts, **Then** it is unaffected by data left behind by the first.
3. **Given** a query or mapping that behaves differently on Postgres than on H2, **When** the affected test runs, **Then** it exercises Postgres semantics, so such a difference surfaces as a test failure rather than a production surprise.

---

### User Story 6 - H2 is gone from the project (Priority: P3)

H2 currently appears as a runtime dependency, twice as an `spring-boot-h2console` dependency, in five `application.properties` settings, in the H2 console route, in onboarding documentation, and as tracked `.mv.db`/`.trace.db` database files in two different `data/` directories.

**Why this priority**: An explicit Definition of Done item, and leftovers are how a developer accidentally ends up back on H2. Lowest priority because it is cleanup, not capability.

**Independent Test**: Search the repository for H2 dependencies, properties, console references and database files, and confirm none remain.

**Acceptance Scenarios**:

1. **Given** the build files, **When** they are inspected, **Then** no H2 or H2-console dependency remains in any scope.
2. **Given** the application configuration, **When** it is inspected, **Then** no `spring.h2.*` setting and no H2 JDBC URL, driver or credential remains.
3. **Given** the repository, **When** it is inspected, **Then** no `.mv.db` or `.trace.db` file is tracked by git, and the ignore rules that already cover them are effective because the files are no longer tracked.
4. **Given** onboarding documentation, **When** a new developer follows it, **Then** it describes connecting to Postgres and contains no instruction to use the H2 console or to delete an H2 file to fix schema drift.

### Edge Cases

- **Identity sequence desync after seeding.** The seed inserts explicit primary keys (customers 900001-900100, accounts 900001-900235, goals 900001-900089). In Postgres, inserting an explicit value into an identity/serial column does not advance that column's sequence, so the next application-generated insert can collide with a seeded row. The seeding procedure must leave every affected sequence set above the highest seeded value.
- **Identifier case folding.** The seed uses unquoted uppercase identifiers (`INSERT INTO CUSTOMERS (CUSTOMER_ID, ...)`). H2 folds these to uppercase, Postgres folds them to lowercase. Because they are unquoted on both sides and Hibernate creates lowercase names on Postgres, they resolve - but any identifier that gets quoted during migration work would break this, so quoting must not be introduced.
- **Dialect in the existing schema script.** `V003__create_audit_log.sql` uses `BIGINT AUTO_INCREMENT` and `CLOB`, neither of which is valid Postgres. `V001` and `V002` must be checked for the same class of problem before being adopted as migrations.
- **An existing developer database that predates migrations.** A developer who already has data will have a database with no migration history. Per the Assumptions, existing local data is disposable, so the defined answer is drop-and-recreate followed by migrate-and-seed; this MUST be documented rather than left to each developer to discover when Flyway refuses to run against a non-empty, unversioned database.
- **Constraint-violation error shape changes.** Postgres reports unique/foreign-key violations with different SQLState codes and messages than H2. Anything that inspects those messages, and the generic `Exception` handler in `GlobalExceptionHandler`, should be checked so a violation still surfaces as the same HTTP status it does today.
- **Two `data/` directories.** `data/` at the repo root and `backend/data/` both currently exist and both hold H2 files, depending on which directory the app was launched from. Both must be dealt with, not just the one in use on a given machine.
- **Losing the H2 console.** The console at `/h2-console` is today's only in-app way to inspect data ad hoc, and onboarding documentation points developers at it for exactly the schema-drift repairs this ticket eliminates. Its removal needs a documented replacement (a `psql` invocation or a GUI client and its connection details).
- **The chatbot's `@PostConstruct` schema bootstrap.** `ChatInteractionLogRepository.ensureSchema()` creates its table at startup on the chatbot datasource. That path is out of scope here, but it must not be accidentally folded into the new primary-datasource migrations, since the two datasources remain distinct.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: The primary datasource MUST connect to PostgreSQL. `spring.datasource.url`, `driverClassName`, `username` and `password` MUST be replaced with Postgres values supplied through environment variables with local-development defaults, following the pattern the chatbot datasource already uses (`${CHATBOT_DB_URL:jdbc:postgresql://localhost:5433/banking_chat}`).
- **FR-002**: Core banking data MUST live in its own database on the existing `banking-pgvector` Postgres server, separate from the chatbot's `banking_chat` database. The two datasources remain logically distinct, so `PrimaryDataSourceConfig` and `ChatbotDataSourceConfig` keep their current split and no chatbot behavior changes.
- **FR-003**: `PrimaryDataSourceConfig` MUST continue to declare the `@Primary` `DataSource` bean explicitly. Boot's datasource auto-configuration stays disabled by the presence of `ChatbotDataSourceConfig`'s `DataSource` bean, so removing or implicitly relying on auto-configuration would bind the application to the wrong database.
- **FR-004**: Schema MUST be managed by Flyway. The Flyway dependency MUST be added, and `backend/src/main/resources/db/migration/V001__create_savings_goals.sql`, `V002__account_control_freeze_unfreeze.sql` and `V003__create_audit_log.sql` MUST be reviewed and rewritten as valid Postgres so they can serve as the initial migration set.
- **FR-005**: The migration set MUST cover every entity the application maps, not only the three tables that happen to have scripts today. Tables currently created implicitly by `ddl-auto=update` MUST be expressed as migrations.
- **FR-006**: `spring.jpa.hibernate.ddl-auto` MUST be set to `validate`, so a mismatch between entity mappings and the migrated schema fails at startup rather than being silently patched or silently ignored.
- **FR-007**: `spring.sql.init.mode=always` and `spring.sql.init.schema-locations` MUST be removed, since Flyway takes over schema creation and the referenced script is H2 dialect.
- **FR-008**: The demo seed MUST be loadable into Postgres. `seed_demo_data.sql` MUST run to completion against a migrated Postgres schema, and `generate_seed.py` MUST emit Postgres-compatible SQL for future regeneration.
- **FR-009**: The seeding procedure MUST advance every identity sequence past the highest explicitly-seeded primary key, so application-generated inserts do not collide with seeded rows.
- **FR-010**: `unseed_demo_data.sql` MUST continue to remove exactly the rows the seed inserts, on Postgres.
- **FR-011**: Repository and integration tests MUST run against a real Postgres instance provisioned by Testcontainers, replacing `@DataJpaTest`'s embedded-database behavior for the thirteen repository test classes and `AuthCustomerIntegrationTest`.
- **FR-012**: Each test class MUST start from a known database state, so tests do not depend on execution order or on data left by a previous run.
- **FR-013**: The H2 dependency, both `spring-boot-h2console` dependencies (one at runtime scope, one with no scope declared), and every `spring.h2.*` property MUST be removed from the build and configuration.
- **FR-014**: The tracked H2 database files (`backend/data/digitalbankdb.mv.db`, `data/digitalbankdb.mv.db`, `data/digitalbankdb.trace.db`) MUST be untracked from git, and both `data/` directories MUST be removed from the working tree. The existing `.gitignore` rules covering `data/`, `backend/data/` and `*.mv.db` already exist and become effective once the files are untracked.
- **FR-015**: No feature logic, entity mapping, repository method, service behavior or API contract may change as part of this work, except where a change is strictly required by Postgres dialect or by the removal of H2.
- **FR-016**: The chatbot's pgvector datasource, its `@PostConstruct` schema bootstrap in `ChatInteractionLogRepository`, and `KnowledgeBaseIngestionRunner` MUST remain unchanged and continue to operate on their own database.

### Contract & Error Semantics Requirements _(mandatory for API or integration changes)_

- **CER-001**: Every REST contract is unchanged. No request or response shape, status code or error code changes as a result of this migration.
- **CER-002**: A database constraint violation MUST continue to produce the same HTTP status and error code it produces today, despite Postgres reporting different SQLState values and messages than H2.
- **CER-003**: A failure to reach the primary database at startup MUST fail fast with an error that names the database connection as the cause, rather than starting the application in a partially-usable state.
- **CER-004**: A schema/mapping mismatch detected by `ddl-auto=validate` MUST fail startup with an error naming the offending table or column.

### Operational & Configuration Requirements _(mandatory for this feature)_

- **OCR-001**: `docker-compose.yml` MUST provide the core banking database alongside the existing chatbot database on the `banking-pgvector` service, so a developer gets both from a single `docker compose up -d`.
- **OCR-002**: Every connection setting for the primary datasource MUST be overridable by environment variable, with defaults that work for local development, so QA and demo environments are configured purely by environment rather than by code changes.
- **OCR-003**: Provisioning managed Postgres for deployed QA and demo environments is out of scope for this ticket (see Assumptions). This ticket delivers the local and docker-compose setup plus the configuration surface those environments consume.
- **OCR-004**: `SETUP.md` MUST be updated: Postgres as a prerequisite, the compose step, how to apply and remove the demo seed, how to connect for ad-hoc queries now that the H2 console is gone, and removal of the H2 schema-drift and two-`data/`-folders gotchas, which no longer apply.
- **OCR-005**: The procedure for applying the demo seed MUST be documented. It is currently an undocumented manual step - `seed_demo_data.sql` is referenced nowhere in configuration or documentation.
- **OCR-006**: Running the test suite MUST be documented as requiring a working Docker daemon, since Testcontainers provisions the test database.

### Key Entities _(include if feature involves data)_

- **No entity changes.** No JPA entity is added, removed or remapped by this feature. The tables change host, not shape.
- **`flyway_schema_history`** (new, primary Postgres database): Flyway's own migration ledger. Created and maintained by Flyway; not mapped as an entity.
- **`audit_log`** (existing): moves to Postgres. Its script (`V003`) is currently H2 dialect (`BIGINT AUTO_INCREMENT`, `CLOB`) and must be rewritten. This is the table whose drift under `ddl-auto=update` produced the missing-column failures this ticket removes the cause of.
- **`chat_interaction_log`** and the pgvector knowledge-base table (existing, chatbot database): unchanged, on their own datasource, not migrated by Flyway.
- **Demo seed dataset** (existing, `backend/scripts/seed_demo_data.sql`): 100 customers, 235 accounts, 26,170 transactions, 89 savings goals across four risk personas, 12 months of history ending 2026-08-01, reproducible from `generate_seed.py` at RNG seed 42.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: The backend starts against Postgres with zero errors, in 100% of attempts, with no H2 artifact present on the classpath or on disk.
- **SC-002**: Data written through the API is still present and identical after a full application restart, in 100% of attempts.
- **SC-003**: Applying all migrations to an empty database produces a schema that passes `ddl-auto=validate` for every entity, with zero validation errors.
- **SC-004**: The demo seed loads into a freshly migrated database with zero errors and produces the documented row counts and persona distribution exactly.
- **SC-005**: After seeding, 100% of application-generated inserts across the affected tables succeed without primary-key collision.
- **SC-006**: One representative read and one representative write succeed for each of the seven named feature areas (Chatbot, Agent, Tools, RAG, Insights, OPS, Risk) against Postgres.
- **SC-007**: The full backend test suite passes with H2 absent from the build, and passes again on an immediately repeated run without any manual database cleanup.
- **SC-008**: A repository-wide search for H2 dependencies, `spring.h2.*` properties, H2 JDBC URLs and `.mv.db`/`.trace.db` files returns zero results.
- **SC-009**: QA executes the same scenario twice from the same seeded starting state and observes identical results both times.

## Assumptions

- **One Postgres server, two databases**: core banking data gets its own database on the existing `banking-pgvector` container rather than a second container or a shared database with two schemas. This keeps the current two-datasource code structure intact and adds no new service to run, at the cost of coupling the two databases' uptime, which is already the case for local development.
- **Flyway is adopted as part of this ticket, not deferred**: the Definition of Done's repeatability criterion is not satisfiable while schema is derived by `ddl-auto=update`, and the `V00N__` files already present are named for Flyway. `ddl-auto` moves to `validate` rather than being removed, so mapping drift is caught at startup.
- **Testcontainers for tests**: repository and integration tests get a real Postgres rather than keeping H2 at test scope. This is what makes "H2 fully removed" literally true and closes the dialect gap between tests and production. It makes Docker a hard prerequisite for running the test suite.
- **Cloud provisioning is out of scope**: this ticket covers local and docker-compose setup plus the environment-variable configuration surface. Standing up managed Postgres for deployed QA and demo environments, and wiring secrets in the existing Cloud Build and Kubernetes manifests, is separate work.
- **Existing local data is disposable**: developers' current H2 data is local demo data reproducible from the seed. No data migration from H2 to Postgres is in scope; developers move over by running migrations and re-seeding.
- **The chatbot side is untouched**: the pgvector datasource, knowledge-base ingestion, `chat_interaction_log` and its `@PostConstruct` bootstrap keep working exactly as they do now. Only the primary datasource moves.
- **No behavior change is acceptable as a side effect**: any observable difference in API behavior discovered during this work is a defect in the migration, not an accepted consequence of it, unless it is a documented, unavoidable dialect difference.
